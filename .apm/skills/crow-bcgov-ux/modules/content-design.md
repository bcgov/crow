# Interface Content Design

Load this module when creating, editing, or reviewing user-facing interface text: page titles, headings, instructions, labels, hints, status and error messages, and calls to action. The [content and feedback](foundations.md#content-and-feedback) rules in foundations still apply; this module does not repeat them.

## Sources

- [Web Style Guide](https://www2.gov.bc.ca/gov/content/governments/services-for-government/service-experience-digital-delivery/web-content-development-guides/web-style-guide) for capitalization, formatting, links, lists, dates, and punctuation.
- [Inclusive language and terms](https://www2.gov.bc.ca/gov/content/home/accessible-government/toolkit/audience-diversity/inclusive-language-and-terms).
- [Writing guide for Indigenous content](https://www2.gov.bc.ca/gov/content/governments/services-for-government/service-experience-digital-delivery/web-content-development-guides/web-style-guide/writing-guide-for-indigenous-content) when content concerns Indigenous Peoples, communities, places, languages, or relationships.
- Product-approved terminology and content standards.

These rules adapt the content design section of the B.C. Design System's [`AGENTS.example.md`](https://github.com/bcgov/design-system/blob/main/AGENTS.example.md).

## Approved content and terminology

- Preserve approved, legal, and policy text unless the user asks to change it. Report readability, accessibility, or inclusive-language findings against it instead of rewriting it silently.
- Keep product-approved terminology. When it conflicts with these sources, keep it and flag the conflict. Approved terminology is never exempt from accessibility or inclusive-language findings.

## Writing standards

- Start with the user's need and task, not the organization's perspective. Make clear what users need to know or do.
- Put the most important information first.
- Write for a Grade 8 reading level or lower.
- Use active voice. Aim for sentences of 20 words or fewer where practical.
- Make content easy to scan with descriptive headings, short paragraphs, and lists where appropriate.
- Use sentence case for headings, buttons, labels, and other interface text unless a proper noun or official name requires capitals.
- Apply the Web Style Guide's rules for capitalization, formatting, links, lists, dates, and punctuation.
- Use inclusive language that a broad public audience can understand.
- Make calls to action specific so users know what will happen when they act.

## Readability measurement

- Measure the Flesch-Kincaid grade level of body copy, instructions, and messages with the project's existing tool or an established readability tool already available. Do not add a project dependency only to measure readability without agreement. Single labels and short button text are not meaningful samples.
- Record the tool, its version, the text measured, and the score.
- Never estimate a score without a tool. If no tool is available, report readability as not measured and list it as an open check, not a pass.
- Do not change required legal or policy meaning to reach a score; report the finding instead.

## Facts you must not invent

Do not invent, infer, or assume requirements, eligibility criteria, required documents, fees, deadlines, processing times, legal information, or contact information.

- When a fact is missing, identify what is missing and ask. Ask whenever missing information or uncertainty could affect meaning, accuracy, or a user's ability to complete the task.
- A missing fact blocks only the affected copy; unrelated work can continue.
- Use a placeholder only in a draft or prototype the user has explicitly accepted as non-production. Make it obvious and searchable, such as `[CONFIRM: application fee]`, and list each one as an open item.
